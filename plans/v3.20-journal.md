# v3.20 A map journal and nightly backups: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A wrong merge, clustering, or edit can be undone exactly, and a map can be rebuilt from its source, before embeddings arrive (v3.24). Lerni's data is also copied every night.

**Architecture:**
- **The journal (`journal.py`, new):**
  - **Where:** `<data>/maps/<user>.events.jsonl`, one line per map change, appended. It's kept as long as the map.
  - **What each line holds:**
    - `n` (1, 2, …), `time`, and `by`: `tagger`, `person:<username>`, `upload`, `educator chat`, or `admin`;
    - `changes`: the before and after of only what changed:
      - each entry that changed, by id (whole entry dicts, `None` when added or removed);
      - links added and removed (whole link dicts);
      - the top-level fields that changed (`removed`, `removed_info`, `archived`, `not_same`, `next_id`, `edits`), before and after.
  - **The baseline:** the first time an existing map changes, a `baseline` line holding the whole map is written first. So replaying the journal from line 1 always gives the current map.
  - **Never message text:** a map already holds only names, notes people wrote, ids, and dates (rule 6), and the journal holds the same.
  - **The calls:**
    - `diff(before, after) -> dict | None`: `None` when nothing changed, so no line is written;
    - `MapJournal.append`, `read`;
    - `replay(events, upto=None) -> dict`;
    - `undo(current, event) -> dict`, which raises `JournalError` when a later event touched the same entries or links. Undoing an older change never wipes a newer one silently.
- **Hooking it in (`interests.py`):**
  - **Every write is journaled:** `MapStore.change(username, fn, by="server")` writes the map, then appends the diff. Every map write already goes through `change`.
  - **Callers say who they are:**
    - `tagging.py`: `tagger`;
    - `web/maps.py` `_act` and the list's edits: `person:<viewer>`;
    - Upload's proposals: `upload`;
    - the MentalMaps chat proposals: `educator chat`.
  - **Two processes at once:** `change` takes a per-user `fcntl.flock` on `<user>.lock` beside the map, so the `lerni map` commands and the running server never write at the same moment. The thread lock stays for the server's own threads.
  - **Best effort:** a journal write that fails (`OSError`) is printed as a count, never text, and never stops the map change. The nightly backup still covers it.
- **Admin commands (`commands/map.py`, new; `lerni map …`):**
  - `log USER [--last 20]`: number, time, who, and a one-line summary ("+volcanoes", "merged T-Rex into Tyrannosaurus", "goal Fractions: notes"). Names only.
  - `undo USER N`: reverses change N, as a new change `by="admin"`, so an undo can itself be undone. It refuses with the conflicting change numbers when a later change touched the same items.
  - `rebuild USER [--upto N]`:
    - **With `--upto`:** writes the map as it was after change N (journaled `by="admin"`).
    - **Without it:** checks that replaying the journal gives today's map, and says so.
- **Nightly backups (`backup.py`, new; `commands/backup.py`; `service.py`):**
  - **`lerni backup run`:** copies the production data folder to `~/.lerni/backups/student/nightly-YYYY-MM-DD/` (each data folder its own, after review) (`shutil.copytree`; maps are written atomically, so each file is whole).
    - It keeps the newest 30 `nightly-*` folders and never touches other folders (the manual `student-before-*` copies).
    - `--to PATH` makes a second copy, for example on an external drive.
  - **`lerni backup install`:** a third LaunchAgent, `com.lerni.backup`, runs `lerni backup run` at 03:00 every day (`StartCalendarInterval`, no `KeepAlive`), with production's data folder. `lerni service status` lists it. Built with the existing `service.py` helpers.
  - **Restoring:** the admin reference gets the steps: stop production, move the data folder aside, copy a nightly folder back, start production.
  - **What it protects against:** these backups are on the same disk, so they cover bad merges, edits, and deploys, not a broken disk. `--to` (or Time Machine) covers that; it's a to-do.

**Tech Stack:** Python 3.11+ standard library (`fcntl`, `shutil`, `plistlib`), typer, pytest.

## Global Constraints

- **Rule 6:** the journal holds what maps hold (names, notes people wrote, ids, dates), never message text. CLAUDE.md rule 6 adds "map change journals" and "nightly copies".
- **Rule 5:** an undo is the admin's act, journaled as `admin`. It can put a goal back as it was, which is a person's decision, never an automatic one.
- **Rule 8:** journals and backups live only on the home server and are never committed.
- **Rollbacks:** older code ignores `.events.jsonl` and `.lock` files, so rolling back to v3.19 is safe; changes made meanwhile aren't journaled.
- **Tests:**
  1. `test_journal.py`, `test_a_bad_merge_can_be_undone_and_the_map_rebuilt`:
     - a map with history gets a baseline;
     - a tagger merge (T-Rex into Tyrannosaurus), then a person's unrelated edit;
     - undoing the merge brings both items back with their days and links, and keeps the edit;
     - undoing an event that a later one touched raises `JournalError`;
     - replaying the journal equals the saved map.
  2. `test_backup.py`, `test_nightly_backups_copy_everything_and_keep_thirty`: a run copies the data folder; with 32 `nightly-*` folders plus a `student-before-x`, the oldest 2 nightlies go and the manual copy stays.
  3. The existing service test gains the backup agent's `StartCalendarInterval` and its data folder.
- **No screen changes.**

## Review Focus

1. **Undo after a merge renumbered nothing but moved links:** the diff by link identity (a, b, kind) restores exactly; `day`/`days` changes count as a change to that link.
2. **The `edits` counter** changes on every person's edit, so it isn't counted as a conflict (it's a counter, not an item).
3. **Two server threads and a CLI command at once:** the flock and thread lock order never deadlocks (thread lock first, then flock, released in reverse).
4. **A journal whose last line was cut off** (a crash mid-write): `read` skips it, and `rebuild` reports a mismatch instead of writing.
5. **Backup during a write:** atomic renames mean each file is whole; a map and its journal may be one change apart, which `rebuild` reports.
